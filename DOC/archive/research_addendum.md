# 效能優化研究報告附錄：最終策略對決

## 1. 背景

在完成 `research.md` 中的初步研究後，我們根據使用者的建議，設計並測試了一種全新的、結合了「預烘烤」和「分段式加載」思想的終極方案：「微型預烘烤」。

本附錄旨在記錄對此方案的測試結果，並將其與前一輪的冠軍方案「分段式加載 + uv」進行最終的正面对決。

## 2. 最終對決方案說明

1.  **方案 A: 分段式加載 + uv (即時安裝)**
    *   **原理**: 啟動時，使用 `pip` 即時安裝啟動「狀態伺服器」所需的 `fastapi` 和 `uvicorn` (此過程極快，約 1-2 秒)，然後啟動狀態伺服器。
    *   **優點**: 邏輯簡單，不依賴任何外部快取檔案。
    *   **缺點**: 每次啟動都需要執行一次 `pip install` 指令。

2.  **方案 B: 微型預烘烤 (解壓縮快取)**
    *   **原理**: 啟動時，不執行安裝指令，而是解壓縮一個預先製作好的、僅包含 `fastapi` 和 `uvicorn` 的微型快取包 (`status_server_deps.tar.gz`)，然後啟動狀態伺服器。
    *   **優點**: 理論上，檔案I/O（解壓縮）可能比網路I/O（安裝）更快。
    *   **缺點**: 實作較複雜，需要額外產生並維護一個快取包。

## 3. 對決結果：網址可用時間

「網址可用時間」是衡量這兩種方案優劣的唯一關鍵指標。

| 方案 | 網址可用時間 (秒) |
| :--- | :--- |
| **A: 分段式加載 + uv (即時安裝)** | 3.08 |
| **B: 微型預烘烤 (解壓縮快取)** | **3.00** |

## 4. 最終結論與建議

測試結果表明，**兩種方案的效能表現處於同一水平，幾乎沒有差異**。

「微型預烘烤」方案雖然在數字上以 0.08 秒的微弱優勢勝出，但這個差距在實際應用中完全可以忽略不計。

然而，在**實作複雜度**和**維護成本**上，「分段式加載 + uv」方案的優勢則非常明顯：
*   **更簡潔**: 不需要 `create_minimal_cache.py` 這個額外的腳本。
*   **更獨立**: 不依賴一個必須預先存在的 `status_server_deps.tar.gz` 檔案。
*   **更穩健**: 減少了檔案解壓縮等潛在的 I/O 失敗點。

**最終建議：**

綜合考慮「微乎其微的效能差異」與「顯著的複雜度差異」，我強烈建議採用 **「方案 A：分段式加載 + uv」** 作為我們專案的最終優化方案。

它在提供了頂級效能的同時，也保持了啟動腳本的簡潔與穩健。我將以此方案來更新 `runner/localtest.py`。
