# Bug Report & System Analysis (2025-08-19)

本文件旨在記錄目前系統遇到的問題、分析其根本原因，並為後續的修復工作提供依據。

## 總結 (Executive Summary)

系統的核心問題源於**設定與整合層面的脫節**，而非後端業務邏輯的缺失。主要問題包括：一個關鍵的啟動腳本 (`Colabpro.py`) 無法以預期的「完整模式」運行、系統啟動流程緩慢、以及數個前後端整合功能（歷史紀錄、狀態更新）失效。

以下是針對各個問題的詳細分析。

---

## 1. 嚴重等級：【高】核心錯誤：`Colabpro.py` 被強制以「模擬模式」運行

**現象**：
使用者回報，即使 `Colabpro.py` 被設計為以「完整模式」啟動，但系統日誌顯示 `orchestrator.py` 仍然以「模擬模式 (Mock)」啟動。這導致所有需要真實外部依賴（如 `yt-dlp`）的功能完全失效。

**根本原因分析**：
經過對 `Colabpro.py` 和 `src/core/orchestrator.py` 的交叉比對，問題原因已非常明確：
1.  **`Colabpro.py` 的意圖**：此腳本的設計是正確的。它會安裝所有真實依賴 (`requirements-worker.txt`)，並在啟動 `orchestrator.py` 時**不**傳遞 `--mock` 旗標，意圖啟動「真實模式」。
2.  **`orchestrator.py` 的缺陷**：在 `Colabpro.py` 指定的舊版本 (tag `4.1.5`) 中，`orchestrator.py` 腳本內部可能存在**強制覆寫**或**錯誤的預設值**，導致它無視外部的啟動參數，頑固地以「模擬模式」運行。目前最新版的 `orchestrator.py` 程式碼已修復此問題 (預設為真實模式)，但 `Colabpro.py` 仍在使用有問題的舊版本。

**結論**：
這是必須解決的第一個障礙。`Colabpro.py` 的功能被 `orchestrator.py` 的內部錯誤完全癱瘓。

---

## 2. 嚴重等級：【中】效能問題：系統啟動時間過長

**現象**：
使用者反應 `Colabpro.py` 啟動的網頁載入時間過久。

**根本原因分析**：
`Colabpro.py` 執行了非常長的**同步啟動鏈**：
1.  刪除舊資料夾 (如果設定)。
2.  `git clone` 下載完整程式碼。
3.  `apt-get install ffmpeg` 安裝系統依賴。
4.  `uv pip install` 安裝兩份 `requirements.txt` 檔案。
5.  啟動臨時網頁伺服器。
6.  透過 `google.colab.kernel.proxyPort` 反覆嘗試取得代理網址。
7.  關閉臨時伺服器。
8.  最後才啟動 `orchestrator.py` 主程式。

這個過程中的每一步都是阻塞的，導致使用者需要漫長的等待才能看到應用程式介面。

---

## 3. 嚴重等級：【中】功能遺失：歷史紀錄未能在啟動時載入

**現象**：
使用者期望在網頁啟動時，能看到先前已處理完成的任務歷史列表。此功能在舊架構中存在，但在遷移後遺失。

**根本原因分析**：
`AGENTS.md` 文件指出，舊的業務邏輯 (`api_server_old.py`) 已被合併到新的 `src/api/api_server.py`。此問題的原因可能有兩種：
1.  **後端 API 缺失**：`api_server.py` 中可能沒有提供 `/history` 或類似的 API 端點來讓前端獲取歷史資料。
2.  **前端整合失敗**：後端 API 存在，但 Vue.js 前端沒有在頁面載入時呼叫此 API，或無法正確解析回傳的資料。

需要進一步檢查 `api_server.py` 的路由和 `vue-app` 的前端程式碼來確定。

---

## 4. 嚴重等級：【低】功能缺失與需求：任務計時器與錯誤處理

**現象**：
使用者提出了兩項新的功能需求，以改善使用者體驗。

**需求分析**：
1.  **狀態計時器**：在前端處理任務的狀態旁，增加一個「計時器」，顯示任務已進行了多久。這需要在後端的工作狀態更新中，加入時間戳或計時資訊，並透過 WebSocket 推送給前端。
2.  **連結處理錯誤顯示**：當使用者輸入的連結無法被後端套件（如 `yt-dlp`）處理時，系統應捕捉這個錯誤，並將錯誤訊息回傳給前端，在頁面上清晰地展示給使用者。這需要修改後端的任務處理邏輯，增加 `try...except` 區塊來捕獲特定異常。

---

## 5. 其他發現：架構複雜性

**觀察**：
專案存在至少三種不同的啟動方式 (`Colabpro.py`, `runner/localrun.py`, `runner/localrun_new.py`) 和兩種不同的背景工作者架構（整合式 vs. 獨立式）。這種複雜性是導致設定錯誤和功能不一致的溫床。

---

## 6. 新增發現：效能瓶頸的量化數據 (2025-08-19)

**背景**：
為了精準定位啟動緩慢的原因，並量化「預先烘烤」策略的潛在效益，我建立並執行了一個臨時的效能測試腳本 (`runner/test_startup_performance.py`)。

**測試目標**：
此測試旨在模擬 `Colabpro.py` 從頭開始安裝所有 Python 依賴 (`requirements-server.txt` 和 `requirements-worker.txt`) 的完整過程，並測量其耗時。

**測試結果**：
經過實際測量，完整的依賴安裝過程總耗時為 **108.69 秒**。

**結論**：
這超過 1.8 分鐘的安裝時間是導致使用者在啟動 `Colabpro.py` 時感到極度緩慢的主要原因。這段時間是純粹的 I/O 和 CPU 密集型操作，並且在 Colab 環境中每次啟動都會重複執行。

採用「預先烘烤」策略，即將這 108 秒的安裝過程替換為幾秒鐘的解壓縮過程，將會是解決此效能問題最直接、最有效的方法。
